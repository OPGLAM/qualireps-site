This is a read-only audit of `qualireps-v2` at `807198f` (`main`), plus the sibling repo `qualireps-site` at `8e58508`. Nothing was edited, committed or run in either repo. This file is the only output.

**How to read it**
- `file:line` paths are relative to the qualireps-v2 root unless prefixed `site:`.
- **(deduced)** means the conclusion comes from reading the code path, not from running the app.
- **not verified** means the claim could not be checked here. Each one says what would check it.

## Most consequential findings

1. **A hand-edited backup unlocks the paid tier with no license key.** ✔
   - `importBackup` (`src/lib/db/backup.ts:179-233`) restores the backup's settings row as it stands. The only fields it keeps from the device are `DEVICE_LOCAL_SETTINGS_KEYS` (`:29-46`), and `entitlement` is not one of them.
   - Nothing validates the key: not on import, and not on load (`stores/settings.svelte.ts:34-45`). `isPaid` is just `entitlement === 'paid'` (`settings.svelte.ts:99-101`).
   - So changing `"entitlement":"free"` to `"paid"` in an exported file and importing it unlocks the app.
   - CLAUDE.md accepts that a backup *holding a genuine key* is transferable. This goes further than that.
2. **The site's refund policy promises something the code cannot do.** ✔
   - `site:REFUND.md:23` says: "A license key from a refunded purchase is invalidated." Keys are verified offline with Ed25519 (`src/lib/utils/license.ts`). There is no revocation list, and the webhook has no refund handler (`site:src/pages/api/paddle/webhook.ts`).
   - Related: `site:PRIVACY.md:13` says no personal data is "transmitted". The site server does fetch the buyer's email from Paddle and sends it to Resend to deliver the key (`site:src/pages/api/paddle/webhook.ts:60,71`, `site:src/server/email.ts:26-34`).
3. **The kettlebell press chain is live, not dormant.** ✔ It is in `CHAINS` (`src/lib/data/chains.ts:216-221`) and is a tile in the new-exercise grid, open to free users too.
   - Meanwhile the site is inconsistent: `site:pricing.astro:21` lists "The bodyweight chains: push, pull, squat", while `site:buy.astro:28` says "all four chains".
   - Removing the chain needs a data migration. Without one, existing kettlebell exercises show "Hero Path · Level 4 of 0", a "Change level" button that opens a blank screen, and a free user can be permanently locked out (section 7).
4. **Several rules hold only in the screens, not where the data is written.**
   - The 3-active-exercise cap is checked only by the Home "+" button and the History restore button. `newExerciseFlow.commit()` does not check it.
   - Recovery state is checked only when a screen opens. The functions that write sets, retests and level changes do not re-check it.
   - The "Already performed" max path is never gated, so it works during the 24 h lock, on rest days, and with future dates.
   - The longer recovery window for sets taken close to failure fires even for users who follow the dose exactly, when their max is 1 or 2 reps (✔ `recovery.ts:115-119` + `dose.ts:12`).
   - Copy that says "rest enforced" or "24 h lock" is only true as long as the user goes through the normal screens.

### 1f. Moving to another level
1. **Trigger B** fires when `canonicalMax ≥ passageCriterion` and a next level exists (`triggers.ts:79-87`).
   - Banner: "You've reached this level's passage criterion (n reps). You can progress to {next} when you're ready." with a **Change level** button.
   - The Home card shows "Ready to progress".
   - On the free tier, the button opens the unlock dialog.
2. **`/change-level`** (`ChangeLevelFlow.svelte`; paid only, route guard at `:90`). "Choose your next level." Every level is listed and tagged "Suggested →", "→ Harder", "← Easier" or "Current". Going down and skipping levels are both allowed.
3. **`/change-level/source`.** "Use estimated max" (half the previous max when going up; the previous max when going down, `changeLevelFlow.svelte.ts:270-279`) or "Test max now" (requires `fresh`).
4. **`/change-level/estimate` or `/change-level/test`.** Buttons "Switch to Level n" / "Save max and switch level".
5. **Write:** `changeLevelFlow.commit()` (`stores/changeLevelFlow.svelte.ts:155-253`) does the following.
   - Re-checks `isPaid` (`:170-172`).
   - In one transaction, updates the **same** exercise row: name, kind, unit, criterion, `chainPosition`, max, `lastMaxTestAt`. It also adds a Retest row (`:237-240`).
   - Increments `settings.chainTransitionsCount` (a field nothing reads).

A consequence (deduced): the history, the day sheet and the CSV label **past** sets with the **current** level's name and kind (`logic/export.ts:58-104`). After a two-sided → one-sided change (for example pull L7 → L8), the CSV rows for the older two-sided sets are empty.

### 1g. Creating a custom exercise
- **Paid only.** The Custom tile is locked for free users (`NewExercise.svelte:92`). The write path also refuses it (`logic/freeChoice.ts:67`).
- **The form** (`/new-exercise/custom`, `NewExerciseCustom.svelte`):
  - "Exercise name" (1-40 characters, no control characters)
  - "Unit": Reps / Seconds
  - "Symmetry": Bilateral / Unilateral
  - then the same max-source and max-value steps as a chain exercise.
- **Written as:** `mode:'custom'`, `chainId:null`, `chainPosition:null`, `passageCriterion:null`.
- **What a custom exercise lacks:** levels, a criterion, a weight, a form guide, and "Change level".
- **The only progression signal is Trigger D**, for reps only, at ≥ 15 reps. Its message has no button.

### 1h. Archive, restore, delete
- **Archive.** Menu ⋮ → "Archive" → "Archive this exercise?" Writes `active:false` (`exercises.svelte.ts:124-126`). The history is kept.
- **Restore.** Only from History → Per-exercise → the "Choose exercise" drawer → an archived exercise → "Restore to active" (`HistoryPerExercise.svelte:429-462`).
  - The only check is the 3-active cap, with the message "You have 3 active exercises — archive one first."
  - It does **not** check the one-per-chain rule. Archive pull A, create pull B, restore A, and the user has two active pull exercises (deduced).
- **Delete.** "Delete permanently?" lists how many sets and max tests will be deleted. One transaction deletes the exercise and its sessions and retests (`exercises.svelte.ts:108-121`). The free-choice marker survives.
- **Delete a single set.** Trash icon in the History sessions list. Writes `sessions.delete` (`HistoryPerExercise.svelte:348`). `lastSetAt` is not recomputed, so the deleted set's rest countdown keeps running (deduced).
- **Reset all data** (Settings). Clears exercises, sessions, retests and the two dormant tables. It keeps the entitlement, license, free-choice marker, `hasOnboarded` and `locale` (`src/lib/db/reset.ts:10-65`).

## 3. The rules as implemented

| Rule | What the code does | Enforced where | Does it match GTG_PRINCIPLES.md? |
|---|---|---|---|
| **Dose** | Reps: `max(1, min(floor(max/2), 5))`. Timed: `max(1, floor(max/2))`. One-sided: computed from the weaker side. It **pre-fills** the input; it is not a limit. The user can enter anything from 1 to 999. Timed sets stop automatically at the dose | `dose.ts:12,34` ✔. Shown at `ExerciseScreen.svelte:211-224`, pre-filled at `SetInProgress.svelte:107-134` | Reps formula matches (`GTG_PRINCIPLES.md:180`). **Timed formula differs**: the doc gives `floor(max/2)` with no minimum of 1 (`:186`, and `FOUNDATION_BRIEF.md:85`) |
| **Passage criterion and progression** | Trigger B: `canonicalMax ≥ passageCriterion` and a next level exists. Moving level is never automatic. A paid user can change level at any time from the menu, without B, to any level up or down. The new max is estimated (no lock) or measured (24 h lock) | `triggers.ts:79-87`. Paid check in the route guard (`ChangeLevelFlow.svelte:90`) **and** in `changeLevelFlow.commit()` (`:170-172`) | Consistent with `:400-404`. The doc's guidance that "the next step must allow at least 4-6 clean reps" (`:408`) is not enforced. Pull L12 and squat L10 are summits with a criterion of 3 that can never fire, yet the screen still shows "Criterion 3 reps" (deduced) |
| **Retest** | "Perform now" requires `fresh`. "Already performed" is **always** available, even during the 24 h lock or on a rest day, and accepts any date, including future ones. Every retest is saved as measured. A lower max is allowed | UI only (`UpdateMaxFlow.svelte:81,162-166`). `persist()` does not check recovery | **Diverges** from `RECOVERY_RULES.md:84` ("Re-test max de l'exercice testé — NON" during the lock), and from CLAUDE.md's rule that "any function that writes a Retest or Session must check the recovery state first" |
| **24 h lock** | `armCnsLock`: a measured test less than 24 h old sets the lock to `performedAt`. An active lock is never shortened. An estimate never sets one. It applies to **this exercise only** | `recovery.ts:52-70`. Used by all three writers | Matches RECOVERY_RULES §3.2. Future dates push the lock out (deduced) |
| **Inter-set recovery** | `max(recoveryMinutes, f(reps in reserve))`. Reps in reserve = `maxAtSet − performed`. 1 left gives 8 min; 0 or fewer gives 15 min. It blocks this exercise's next set; it is not advisory | `recovery.ts:85-137,185-230`. Gate: `canLogSet` = `fresh` | The 5-minute default matches GTG_PRINCIPLES §2. But `GTG_PRINCIPLES.md:77` and `:232` still say "15-60 minutes". The comment "never fires for a user following the protocol" (`recovery.ts:125-127`, CLAUDE.md, `RECOVERY_RULES.md:52`) is **false for a max of 1 or 2** ✔: a max of 2 gives a dose of 1 and 1 rep in reserve, so 8 min; a max of 1 gives 0 in reserve, so 15 min and the set is flagged failed |
| **Where the longer window is ignored** | Three screens compute recovery with `exerciseLastSetRir: null`: SetInProgress (`:99` ✔), UpdateMaxFlow (`:77`), ChangeLevelSource (`:107`). After a set taken to failure, the exercise screen shows 15 min while "Perform now" unlocks after 5 (deduced) | — | Inconsistent with RECOVERY_RULES §2.1 bis |

## 4. Free versus paid

- max testing and updating
- dose
- the four recovery states

**Purchase flow, traced:**

### 5b. Offline
- **What is precached:** the service worker (`src/sw.ts:28-29`) precaches every built file matching `**/*.{js,css,html,svg,png,ico,webmanifest,woff,woff2}` (`vite.config.ts:102-104`).
- **Navigation:** every navigation is served the cached `index.html` (`sw.ts:31`).
- **Other requests:** there is no runtime caching, so Paddle and the license API always need the network.
- **Fully offline after the first load (deduced).** Purchasing needs a connection, and the app says so: "You need to be online to purchase." (`UnlockDialog.svelte:95-97`).
- **Dev:** the service worker is disabled in dev (`vite.config.ts:122-124`).

### 5c. Where data lives
- IndexedDB, database `QualiRepsDB` (`db/db.ts:380`).
- No localStorage, sessionStorage or cookies (none used in `src/`).
- Persistent storage is requested with `navigator.storage.persist()` (`stores/storage.svelte.ts:50-55`).

### 5d. Accounts and identifiers
- **No account, email, name or device identifier is asked for or collected.**
- Row IDs are local UUIDs that are never sent anywhere.
- The browser's user-agent string is read only on the device, to choose install instructions.
- **The only identifier that leaves the device is the Paddle transaction id**, sent to the license API and embedded in the key. The key's content is `{"t":"<txn id>","d":"YYYY-MM-DD"}` (`license.ts:8,98-112`): no email or name, but Paddle can link that id to the buyer.

- The iOS text "iOS only installs web apps from Safari… (and Chrome) can't add to the home screen" is probably outdated: since iOS 16.4, other iOS browsers can add to the home screen. That comes from general knowledge and is **not verified** here; a test on a current iPhone would settle it.
